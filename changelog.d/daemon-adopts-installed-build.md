- A running daemon moves to a new build installed at the path it was started from. After a check, on macOS and Linux, a daemon whose start path now leads to a different build file (a moved link such as `current`) checks it: the file and every directory on the way belong to you and no one else can write them (so builds under a group-writable directory such as Homebrew's are not adopted), it speaks the handover, it declares no older state format, and its own `validate` accepts the loop's configuration. It does not switch while its configuration does not load or names another `state_dir`, a transfer is pending, or the owner changed. It then replaces its program in place with that same checked file: the same process and daemon lock, with holds, owner, send counts and state untouched, and nothing of the loop on the command line. A build that fails a check is refused and the daemon carries on; a build that cannot finish starting returns to the earlier one, which is checked first and does not try it again. Each step is recorded in `runs.jsonl` and `build-adoption.json` and shown by `status` and `doctor`, including when a switch leaves no supervisor. `loop.daemon.adopt_installed_build: true` also adopts a file written over in place; `false` turns it off. `start --background` and `service install` now launch through the path they were run by, so a link to the installed build stays a link. Windows daemons keep their build. See [a running daemon moves to the installed build](docs/operations.md#a-running-daemon-moves-to-the-installed-build).

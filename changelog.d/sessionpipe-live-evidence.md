- After a wake of an observed sessionpipe session that was refused, failed or has an unknown outcome, the next wake waits until the session's next turn event or `min_wake_interval`, whichever comes first. Before this, every check sent another attempt while the session read idle, as the first live run showed (sessionpipe 0.18.2, Claude Code 2.1.326, macOS, an isolated lab). `status` and doctor say when the next attempt is due. The docs now record that run: observing held; no wake has yet been delivered to a real session; a headless `claude -p` session cannot be woken; the two `harness` refusals; and that an observed loop's stop sends no stop report. On builds from #520 until this fix, a failing wake was retried at every check and could use up a loop's send budget; afterwards that shows only as the ordinary send-limit hold.

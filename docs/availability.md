# Availability and verification

What each part of looptender does today, which release it is in, and what has and has not been verified. The [README](../README.md) gives the short version.

## Where it works best

BB threads get the most: lane awareness, retrying a failed turn by reference, and the BB plugin. Coordinators still own [reconciling existing lane obligations](coordinating-lanes.md#reconcile-existing-lanes-before-parking-the-coordinator): idle/error/archive status is not completion, and newer owner direction requires explicit assignment review rather than automatic dispatch or hold clearing. Headless Claude Code and Codex sessions get the general behaviour (wakes, limited re-prompts with exact session resume, routes, limits and reports) but nothing for lanes. Cursor and Antigravity run as standalone first routes only and cannot be fallbacks ([Antigravity details](antigravity.md)). In unreleased source, a session sessionpipe reports can be [observed](sessionpipe.md#observed-sessions-in-unreleased): looptender reads its state and holds or reports, and sends it nothing unless the loop opts in to waking it when idle. Agents defined in configuration have been tested only with stand-ins. Much of the rest is fixture-tested and the full live walkthrough is unfinished; the table below says what has been verified where.

In unreleased source, a recognized structured Claude error takes precedence over a success flag or exit zero in turn status and fallback probes. This is covered by local fixtures; it does not establish live provider behavior.

Generic process adapters retain at most 1 MiB of command stdout in unreleased source. Overflow reports an unknown outcome; it is not treated as a configured rate-limit exit. Excess bytes are discarded while the command finishes under its existing timeout. Headless Claude Code and Codex observations read at most 8 MiB of a completed turn; larger output stays unknown and supplies no session or limit evidence. Their private output files are not size-capped. These bounds do not add descendant cleanup or an automatic retry guarantee.

## What is released, in source and verified

**Version guide: CLI [v0.2.0](https://github.com/looptender/looptender/releases/tag/v0.2.0) + BB plugin v0.3.0, from the same tag.** It is distributed under the [Sustainable Use License 1.0](../LICENSE). Its [release notes](releases/v0.2.0.md) say what is new, what changes on upgrade and how to go back. Package evidence is [recorded here](release-verification.md#v020-release-preparation). Check `keepgoing version` for the installed package. Installing a release does not upgrade a separately deployed supervisor executable or install the BB plugin or macOS companion.

Unreleased source adds `looptender session reset` to deliberately forget a saved Claude Code, Codex or resumable defined-agent session. It sends nothing and clears no hold; see [reset behavior and refusals](operations.md#starting-a-new-conversation-on-purpose). This command is not in v0.2.0.

Unreleased CLI `pause` can preserve malformed control bytes in a restrictive freeze on macOS/Linux. Ownership remains unknown and no repair or resume is available. Windows refuses this operation. See [damaged-control limits](operations.md#damaged-control-pause-freeze-unreleased).

Unreleased headless runner completion requires wrapper protocol 3 (previously 2). Before upgrading, stop supervision and let old detached turns finish, or use owned stop and confirm actual exit, then replace/restart. The handshake protects new launches only; see [completion and upgrade limits](operations.md#owned-headless-cancellation).

Unreleased source also allows Windows readers to retain a headless turn record while its replacement is published; [turn-record fixture evidence](testing.md#windows-turn-record-publication) covers that record only. Completion publication and cleanup now stay under the turn lock, with shared completed-status reads fencing rollover. This is fixture-tested source behavior, not installed-service or live-provider acceptance.

The v0.2.0 changes are **not in v0.1.5**: among them network-aware recovery and BB turn retry by reference, holding back nudges to a hung turn, noticing a stopped scheduler, one loop per session, the panel and its controls, agents defined in configuration and the Cursor adapter. The [release notes](releases/v0.2.0.md) list them all; a loop that has run on v0.2.0 needs [these steps](releases/v0.2.0.md#going-back-to-v015) before v0.1.5 can run it again. See the [changelog](../CHANGELOG.md) and [release evidence](release-verification.md) for exact scope.

The complete live setup → multiple turns → hold → restart → recovery → completion walkthrough is still unfinished. Existing tests and package installation do not establish readiness to migrate other threads. The [roadmap](roadmap.md) tracks those acceptance checks separately from implementation.

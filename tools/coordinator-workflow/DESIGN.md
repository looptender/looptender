# Coordinator-owned delegation workflow

Status: design and offline implementation work. Automatic delegation acceptance is **INCOMPLETE** until the packaged coordinator path is exercised by an agent in BB and installed behavior is verified. A passing deterministic harness is not that acceptance.

## First bounded release: new-child dispatch only

Reuse and `thread tell` are EXCLUDED. No supported atomic conditional idle-only dispatch has been established in BB source. A check followed by `tell --mode auto` can steer a turn that starts in between and is not an acceptable substitute. Existing idle unfinished, error, archived and superseded obligations remain in review with typed next actions; the workflow may dispatch independent newly authorized tasks when all gates permit, but never automatically retries or replaces those obligations. Full automatic coordinator acceptance remains INCOMPLETE for reuse and agent/installed behavior.

## Production consumer and authority

The packaged `keepgoing` skill is the coordinator entry point. Under an existing explicit owner grant to delegate specified deliverables, it invokes `scripts/coordinator.py` at assignment/phase settlement rather than asking the person for the same delegation permission again. The coordinator supplies a private, revisioned grant containing the exact parent/project/environment/host/provider/model/effort tuple, scope and authorization references, bounded dispatch attempts, direct-child concurrency ceiling and exclusive resource keys. Grant references are cooperative coordinator declarations, not authentication or a semantic authorization oracle. The script never interprets owner text or a transcript.

This is an agent-side orchestration command. No `tick`, daemon, adapter, decision engine or automatic supervisor path imports or calls it. General supervisor conversation creation remains prohibited. Any future opt-in supervisor dispatch would require a dedicated architecture/capability change, owner/host authorization, durable operation identity and separate review; this workflow does not supply it.

## Real command seam

Read current structured controls with `keepgoing status -c <config> --json`, the validated private record with `keepgoing assignment show -c <config> --private --json`, and bounded direct-child inventory using the existing command. Before dispatch require current goal/owner/config binding, complete inventory and the coordinator's exact expected assignment revision. Existing idle/error children remain obligations, not spare slots or completed work.

The real write is the coordinator's `bb thread spawn --json --parent-thread <parent> --project <project> --environment <environment> --host <host> --provider <provider> --model <model> --reasoning-level <effort> --visibility visible --parent-notifications auto --prompt-file -`. No permission override, login, model probe, provider/account switch, hidden lane or new environment is requested. Task content travels through stdin. Real BB help exposes no idempotency key; a non-success, malformed/lost response or timeout is an unknown creation outcome, never permission to replay.

Before that call, atomically persist a private attempt and reserve its task/resource/attempt allowance. On a verified creation reply, verify the exact child metadata and publish the new assignment mapping with the existing revision-bound `assignment review` writer. Failure of mapping publication does not cause another spawn. An explicit reconciliation names the exact intent and child, revalidates parent/environment and preserves the spent attempt; titles and before/after list differences never infer ownership. A child that cannot be identified keeps the workflow unresolved. There is no automatic timeout-based release.

## Settlement and bounds

Only an explicitly acknowledged current assignment handoff settles an obligation. Complete plus verified idle/no pending input releases its resource; an unfinished handoff keeps ownership; errored execution alone never retries/replaces it. Duplicate handoff revisions do not advance progress. Superseded/archived/disappeared work retains its remaining obligation and requires explicit reassignment review. A newer owner grant revision may reactivate an earlier coordinator-parked task, but never clears a runtime stop/pause/awaiting-user/completed/retired gate.

A settlement runs the next authorized independent dispatch in the same coordinator operation when all gates allow it. Missing declarations, stale revisions, changed binding, unavailable/partial inventory, unknown attempts and pending person gates fence the affected work; global runtime holds fence all dispatch. Healthy busy lanes remain untouched. No unconditional retry, child stop/archive/reparent, implicit resume or transcript inference exists.

The attempt budget is a local dispatch-attempt bound, not a token/currency/quota guarantee. The concurrency observation covers this parent's direct children; a local workflow lock serializes this ledger only. It cannot guarantee global host capacity or exclude independent actors racing after observation. BB host limits remain authoritative. Exclusive keys cover only explicitly participating tasks; external resource users require coordinator review. These limitations must appear in dry-run output and documentation.

## Grant provenance, verification and deployment prerequisites

The exact packaged consumer is `integrations/bb-plugin-keepgoing/skills/keepgoing/scripts/coordinator.py`, referenced relative to the installed skill directory. The agent may write its private grant only as a faithful transcription of an existing owner instruction permitting delegation; it records that instruction's source, scope, explicit new-child creation permission and model/resource/attempt bounds. Writing or signing the file does not manufacture new permission. The workflow cannot authenticate a person or decide whether arbitrary natural-language permission covers a task. It must refuse absent required declarations, and the coordinator must not supply them speculatively.

A `complete` worker handoff or idle execution is insufficient settlement. Require current exact-revision handoff acknowledgement **and** an explicit coordinator verification receipt bound to that handoff and reviewed artifacts. Local artifact digests must still match before settlement. The receipt records the coordinator's acceptance judgment, not an independent proof that arbitrary task requirements were met. The behavioral harness will create/check fictional deliverable artifacts before issuing that receipt, and reject missing/stale/wrong-task artifacts. Repeated receipts do not increment completed-work counts.

Error/archived/superseded obligations remain in the private record with their owner and remaining-work references. Output must expose their typed next reconciliation action and any independent authorized task that can proceed. Do not silently filter them out or permanently abandon them because the dispatcher cannot repair their execution state. Recovering or replacing such work is an explicit coordinator review under existing authority, not an automatic retry rule.

The packaged script requires Python 3 and Unix private-file locking. An unavailable/unsupported interpreter or failed lock is an unavailable workflow, not successful delegation: no install, alternate host, bypass or grant expansion is attempted. The coordinator then uses the existing explicitly authorized BB and assignment commands with a private ledger, or reports this concrete tooling limitation while continuing other authorized work. The script is not registered as a daemon, scheduled job or plugin backend action. Git-distributed plugin skills include the relative script resource; bundle/install inclusion needs its own packaging check before any rollout.


## Required journal and submission fences

- Journal: private regular schema-1 JSON, maximum 256 KiB, 32 tasks and 128 non-evicted attempts/verification receipts. Duplicate keys, unknown fields/versions, nonfinite values, malformed transitions, binding mismatch, missing history or corruption refuse; reads never reset/rebind/repair. One nonblocking Unix lock serializes this journal. Each update writes a 0600 temporary file, flushes/fsyncs it, atomically replaces, then fsyncs the directory. The coordinator lock precedes existing CLI locks; no Go tick/control lock is held during a host request, so ordinary Pause/Stop does not wait for BB submission.
- Unknown spawn reserves its task, resource, one dispatch attempt and one slot across process restart and newer grant revisions. A known child ID deduplicates its reservation against observed identity; two owners/intents for one child refuse. Unknown mapping publication is a separate unresolved state and must be explicitly reconciled against the current exact assignment row before any new mutation. No grant update resets spent attempts or unresolved reservations. A new grant ID cannot adopt an existing journal; missing journals cannot initialize at a later grant revision. Deleting/moving a journal is not a supported reset or recovery.
- Slot release requires a verified complete obligation receipt and current idle/no-pending child evidence. Worker completion alone, idleness, archive, errors and disappearance do not release an unresolved task/resource reservation. Counts include observed active/pending/starting/stopping direct children and owned unresolved identities, deduplicated by exact ID. This is the stated local direct-child bound, not global host concurrency.
- Bind the exact original `BB_THREAD_ID`, configured/current owner generation, goal/revision, canonical config/runtime, assignment record/revision, grant ID/revision and reviewed scope/authorization source hashes. Preserve the entire execution environment. Pin both requested BB executable and its effective `BB_CLI` re-exec target; changes refuse rather than stripping or replacing environment markers. A grant is a cooperative record of existing authority, never cryptographic person proof.
- `assignment show --private` validates stored structure/history only. Independently require current status assignment binding available, exact current goal/owner/primary BB target, clear effective controls/allowances, matching source hashes, and the exact current record revision. Compare a fresh bounded inventory with all reviewed identities; query typed child metadata and interactions because inventory omits pending input and environment/provider identity. Partial/changed/unknown evidence is not zero children.
- Immediately before durable intent and submission, while holding the helper journal lock, repeat current status/owner/goal/source/record checks and ensure controls and binding still match. There is no cross-process/host transaction: a subsequent Pause/Stop/transfer can race a BB request already submitted. Such a request is not rolled back or converted to a confirmed failure; preserve its attempt and report the residual boundary. This helper makes no global atomic-hold claim.
- Execution: one spawn per advance, at most 430 read calls/one write intent per operation; 60-second whole-operation deadline, two-second ordinary read timeout, twenty seconds for existing bounded inventory, fifteen seconds for spawn and ten seconds for assignment publication, with two seconds reserved for cancellation/journal cleanup. Stream stdout into a capped 1 MiB decoder (64 KiB for thread/interaction replies), discard stderr (zero retained bytes), terminate only the owned local CLI process group on cap/timeout and reap within two seconds. Killing the client cannot cancel or prove rollback of a host-side spawn. Exhausted budgets refuse before submission; no retry or unbounded join is allowed.
